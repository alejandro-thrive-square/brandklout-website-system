# 2026-09-10 — The 404 page, and the build is finished

**Instance:** `https://staging.masonparkdental.com`. Production untouched.

## Done

**A branded 404 on every unmatched URL.** Instatic was serving its stock
not-found document — an `<h1>` on a bare `<body>`, no header, no footer, none
of our stylesheet, and no way back except the browser button. `/404` is now a
normal page in the build, marked `templateEnabled` with
`target: {kind:"notFound"}`, so `resolveNotFoundTemplate()` composes it like any
other page and it arrives with the full chrome.

Verified live: `/nope`, `/services/does-not-exist` and `/blog/nothing-here` all
return **status 404** with the right title, `body class="has-journey"`, 58 nav
links and the footer. Six ways back, every destination checked against disk at
build time.

New: `build-404.mjs`, `apply-404-template.mjs`. `stamp-page.mjs` grew a
`"noindex": true` spec flag (drops the canonical and `og:url`, adds a robots
tag). `build-sitemap.mjs` keeps `/404/` out of both sitemaps and out of the
count.

**This finishes the rebuild.** Every page from the old WordPress build now
exists: 55 static pages, the `/blog` listing, the article template, and 161
articles as CMS rows. 57 page rows on staging. All local gates green —
`check.mjs` 223/0, `prune-nav.mjs` every internal link resolves,
`probe-heights.mjs --diff base` unchanged, `link-chips.mjs` 32/32 — and
`verify-live.mjs` clean on all 54 routable pages.

## Gotchas

**`GET /404` returns 200, and that is correct.** The router's own comment says
so: "A direct GET of `/404` … status 200 — identical to how static hosts treat
`404.html`." It is not a soft-404 bug and not worth re-investigating. Nothing
links to it and it is out of `sitemap.xml`.

**The `noindex` meta does not reach the live page, and does not need to.**
`to-instatic.mjs` ships a BODY, not a document — Instatic builds the `<head>`
itself — so the robots tag exists only in the static `home/` build. On the live
site the 404 status code does that job, and does it better than a meta tag.

**`apply-404-template.mjs` runs AFTER any `import-pages.mjs`,** exactly like
`apply-blog-template.mjs`. The site-document save rebuilds each row through
`pageToCells()` and drops the template flags; the moment they are gone, the
stock 404 is back. There are now TWO of these to re-run after every page
import — both are in the order below.

## The order, end to end

```
node to-instatic.mjs --media instatic-media-map.json
RAILWAY_ENV_NAME=staging node ship-payload.mjs          # add --dir pages-templates for the blog pages
RAILWAY_ENV_NAME=staging node run-converter.mjs
RAILWAY_ENV_NAME=staging node fetch-nodes.mjs
node apply-image-alt.mjs                                # BEFORE import-styles
node apply-body-class.mjs                               # BEFORE import-styles
node import-pages.mjs --overwrite
node import-styles.mjs
node apply-blog-template.mjs                            # AFTER import-pages
node apply-404-template.mjs                             # AFTER import-pages
node import-scripts.mjs                                 # AFTER any page id changes
# then publish, then verify-live.mjs
```
