# Fluid Root Font-Size — house standard

> [!IMPORTANT]
> **Every site we build carries this.** It is not an enhancement applied to some projects. A design
> package is not done until `node scripts/fluid-root.mjs --check <package>` exits 0.

## The principle

One fluid root font-size scales the entire design. `html { font-size }` interpolates linearly with
viewport width, so **every `rem` in the stylesheet becomes viewport-relative for free** — type,
spacing, radii, icon sizes, container padding. Nothing needs a per-element media query, and the
design keeps its proportions on a 13" laptop and a 27" monitor instead of stranding a fixed layout
in the middle of a wide screen.

This is the Finsweet Fluid Design Generator technique. We pin it in
[`scripts/fluid-root.mjs`](../../../scripts/fluid-root.mjs) so the emitted CSS is byte-identical on
every client instead of being re-generated by hand per project.

## The scale — `webzite-house-v1`

| Screen width | Root font-size |
| :--- | :--- |
| 320px | 12px |
| 479px → 1440px | 16px (flat) |
| 1920px | 18px |
| 2400px | 20px |

Scaling continues past 2400px and below 320px rather than clamping.

> [!IMPORTANT]
> **The 479 → 1440 segment is flat at 16px on purpose.** 16px is the browser default, so a design
> already sized in `rem` renders **pixel-identical across that whole range** — phone-landscape,
> tablet, laptop and standard desktop are all untouched. Type shrinks only below 479 and grows only
> above 1440. That is where the scale earns its keep: small phones stay readable, and large monitors
> stop stranding a fixed-width design in the middle of the screen.
>
> The curve is deliberately **continuous** — no step at any breakpoint. If you ever change the
> table, keep each segment's `from.px` equal to the previous segment's `to.px`.

Regenerate or inspect at any time:

```bash
node scripts/fluid-root.mjs            # <style> block for <head>
node scripts/fluid-root.mjs --css      # bare CSS for a shared stylesheet
node scripts/fluid-root.mjs --verify   # rendered root px at each breakpoint
```

## How it works

Four inputs per segment; `--coefficient` and `--base` derive from them. Because custom properties
resolve at computed-value time, each media query overrides **only the four inputs** and the derived
values follow automatically — they are never repeated.

```css
--coefficient: calc((var(--font-to) - var(--font-from)) / (var(--vw-to) - var(--vw-from)));
--base: calc((var(--font-from) - var(--vw-from) * var(--coefficient)) / 16);
html { font-size: calc(var(--base) * 1rem + var(--coefficient) * 1vw); }
```

The `/16` and the `* 1rem` are not decoration. Per spec, a `rem` used inside `font-size` **on the
root element** resolves against the *initial* root font-size (16px), not the value being computed —
so the formula is self-consistent rather than circular.

The cascade is authored large → small: the widest segment is the base rule, and each smaller segment
is a `max-width` query. Narrower queries come later, so they win.

## The rules this imposes on design

1. **Size type in `rem`. Never `px`.** A `px` font-size opts that element out of the entire system.
2. **Do not use `clamp()` for font-size.** The root is already doing the fluid work; a `clamp()`
   whose bounds are in `rem` and whose middle term is `vw` scales *twice* and outruns the scale at
   both extremes. Plain `rem` is now correct and sufficient.
3. **Media queries stay in `px`.** A `rem`-based media query is measured against the root font-size
   that the query itself is about to change — a feedback loop with layout thrash at the boundary.
4. **Nothing else may set `html` or `:root` font-size.** One fluid root per page. A CSS reset or a
   vendor stylesheet that sets `font-size: 100%` or `16px` later in the cascade silently kills it.
5. **Spacing, radii and container widths in `rem` too** — that is where most of the benefit is. Keep
   hairline borders and anything that must not scale (e.g. `1px` rules) in `px` deliberately.

### Retrofitting an existing rem-based design

**From 479px to 1440px the root is exactly 16px**, the browser default. So a design that already
sizes in `rem` renders **pixel-identical across that entire range** after installing the snippet —
phone-landscape, tablet, laptop and standard desktop are all unchanged. Nothing to re-approve there.
The risk is confined to the two ends:

- **Wide screens grow**: +12.5% at 1920, +25% at 2400. Check that pinned/scrubbed scenes still fit
  the viewport height and that hero type does not overflow.
- **Small phones shrink**: root is 13.76px at 390 and 12px at 320. **Body copy must still render at
  ≥16px at 390** — that means `≥1.16rem`. Anything left at `1rem` becomes 13.8px, too small for a
  medical audience. Tap targets must stay ≥44px, so size them in `px` or re-check them at 390.

Because 479–1440 is flat, the six-breakpoint QA effectively reduces to **360, 390 and 1920** for
type-scale purposes. The mid-range captures should be byte-identical to the pre-install ones — if
they are not, something else in the cascade is fighting the root.

### Replacing an existing `clamp()` type scale

Do not swap `clamp(3rem, 7vw, 5.2rem)` for an arbitrary `rem`. Pick the value that **preserves the
rendered size at 1440px** (root = 16px, so `rem = px / 16`), then verify the extremes at 390 and
1920 still read correctly and adjust the *scale*, not the individual declaration.

> [!WARNING]
> **Removing a `clamp()` is not a no-op in the mid-range, even though the root is flat there.**
> This is the opposite of the retrofit case above and it catches people out. A `clamp()` whose
> middle term is `vw` was doing its own ramp *inside* 479–1440; a plain `rem` is **constant** across
> that range. So the mid-range captures are byte-identical only for declarations that were already
> bare `rem`. Every `clamp()` you remove changes 479–1440 by design.
>
> Worked example (Grand Mission, 2026-08-07): a hero at `clamp(2.9rem, 7vw, 6.6rem)` rendered 46px
> at 390 and 101px at 1440 — a 2.2× viewport-proportional ramp. The root's own ramp is 0.86×. Set to
> the 1440-preserving `6.3rem`, the 1440 view is exact but a 768 tablet gets a 101px headline, which
> measured turned a 3-line hero into 5 lines and pushed the offer box and proof row below the fold.
> Set low enough for 768, the 1440 hero loses a third of its size and stops out-ranking the section
> headings.

#### When the design's display type is viewport-proportional

Body, labels and captions are near enough root-proportional that a single `rem` covers them. Display
type authored at `5–7vw` is not, and no single `rem` can be both ends of its ramp. When that is the
case, keep the plain-`rem` scale and add a **short px-media staircase on the display tokens only**:

```css
@media (max-width: 1199px) { :root { --d1: 4.4rem; --h2: 2.6rem; } }
@media (max-width: 767px)  { :root { --d1: 3.2rem; --h2: 2.2rem; } }
```

This stays inside every rule above — no `clamp()`, no `px` font-size, no `rem` media query, no root
override — and `--check` passes. Keep it to the two or three tokens that set the fold and the page
rhythm; a staircase on twenty individual declarations means the display sizes should have been
tokens in the first place. Anchor the top step so the **1440 reference view is exact**.

Pick each step against a *measured* overflow ceiling, not a glyph-table estimate. The binding case is
always the single longest word in a headline, because a grid item defaults to `min-width: auto` and
refuses to shrink below it. Measure it by setting the token live and reading the wrapper's
`scrollWidth`, and note that `body { overflow-x: hidden }` — which most of our kits set — means a
document-level overflow check reports **nothing** while the text is silently clipped:

```js
document.documentElement.style.setProperty('--d1', candidate + 'rem')
shell.scrollWidth - shell.clientWidth   // 0 means it fits
```

## Install

Preferred: emit with `--css` into the project's **shared stylesheet**, as the first rule, before any
reset. One place per client, not per page.

For Webflow, paste the `<style>` block into **Site Settings → Custom Code → Head**, not per-page, so
every page inherits it.

> [!TIP]
> This also removes a known Webflow conversion failure: the Designer style panel cannot parse CSS
> functions and displays `clamp()` font sizes as **0px**. Rule 2 eliminates `clamp()` from type, so
> sizes stay legible and editable in the panel after conversion.

## Verification

```bash
node scripts/fluid-root.mjs --check deliver/<client>/workflows/04-design/.tmp/
```

The gate resolves linked stylesheets before judging, so it sees snippets that live in a shared CSS
file. It fails on: missing snippet, a later root `font-size` override, `px` font-size, `clamp()`
font-size, and `rem`-based media queries.

The static gate cannot see rendering. Also confirm during responsive QA that computed
`document.documentElement` font-size matches `--verify` at each captured breakpoint, and that the
479/480 boundary looks deliberate.
