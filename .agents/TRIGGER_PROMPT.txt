TRIGGER PHRASE: @dispatch

When a message contains a line starting with @dispatch, execute the cross-
provider dispatch workflow below. This routes the task to another provider's
agent (Claude / Codex / Pi) and returns its answer. Works on Windows (local)
and the Hostinger VPS identically.

SYNTAX
  @dispatch [async] [diff:N] [account:personal] <role|agent> <task...>
  @dispatch loop [recipe:NAME] <role> [verify:<role>] <goal...>   (autonomous)

  async      optional. If present, queue via handoff (background worker).
             Default is synchronous: run now and return the answer.
  loop       optional VERB. Runs an autonomous produce->verify->refine loop
             that iterates <role> (the producer) against a verifier until the
             verifier approves or a stop cap fires. Use recipe:NAME for a preset
             (design-refine, bug-hunt, doc-tighten, plan-sharpen) or name the
             producer + verify:<role> directly. Loop sub-agents run UNATTENDED in
             permission-bypass mode, confined to a --cwd workspace; the loop
             REFUSES mutating roles (vcs/commit/deploy/publish) and forbids
             publish/deploy/git-push in every prompt. See DISPATCH.md "The
             autonomous loop". Producer/verifier must be non-mutating roles.
  diff:N     OPTIONAL OVERRIDE, 1-10. Omit it by default — the role already
             carries the right model. Only add it to deliberately go cheaper or
             stronger than the role's tier (see WHEN TO OVERRIDE).
  account:   optional, `personal` runs Claude on the personal (Max) account
             instead of the team one. Claude roles only.
  role       a task type from ROUTING below, OR a named agent
             (e.g. codex-automation, pi-lite, claude-review).
  task       free text - the full instruction for the sub-agent.

PICK THE ROLE. THAT IS THE WHOLE DECISION.
The role encodes the task TYPE, and the task type determines the model. You do
not need to rate difficulty — routing already knows that reviewing code needs
Fable and committing a file does not.

ROUTING (role -> agent / model)

  MAX — judgment, critique, strategy                            [Claude Fable]
    review | code-review | audit | bugs   -> claude-review
        review any code, spot bugs and errors
    plan | strategy | system-improvement  -> claude-plan
        planning + strategy, internal or for clients
    design-qa | design-review | ux-review -> claude-design-qa
        review sites, improve desktop/mobile, find design errors

  HEAVY — generative production                     [Claude Opus / Codex Sol]
    design | build                        -> claude-design      (Opus)
        create a new awwwards site or design system
    design2 | build2                      -> claude2-design     (Opus, personal)
        same, on the 2nd account — for a concurrent design job
    automation | backend                  -> codex-automation   (Codex Sol)
        automations for local Windows or the VPS; backend work
    motion | animation | remotion         -> claude-motion      (Opus)
        create an animation in Remotion

  STANDARD — routine execution                    [Claude Sonnet / gpt-5.5]
    site-update | media                   -> claude-site        (Sonnet)
        update a site that already exists; generate images/video
        from any provider (higgsfield, magnific)
    scrape | data                         -> codex-scrape       (gpt-5.5)
        scrape data

  LITE — bookkeeping                                               [GLM 5.2]
    docs | vcs | commit | token-opt | linking -> pi-lite       (pi)
        update the directives with what was learned each task/iteration;
        commit changes to the repo (system updates or client tasks)
    docs2 | vcs2 | commit2 | token-opt2 | linking2 -> opencode-lite  (opencode)
        same, on the 2nd lite worker — for a concurrent bookkeeping job

WHEN TO OVERRIDE WITH diff:N
Only when THIS instance differs from what its role usually implies:
  diff:1-3   lite      -> GLM 5.2 (pi, or opencode on the Z.ai plan)
  diff:4-6   standard  -> Claude Sonnet / Codex gpt-5.5 (medium reasoning)
  diff:7-9   heavy     -> Claude Opus / Codex gpt-5.6-sol (high reasoning)
  diff:10    max       -> Claude Fable
Examples of a real override:
  @dispatch diff:10 backend architect the whole billing retry system
      (a backend task big enough to deserve Fable, not Codex)
  @dispatch diff:2 docs fix the typo in README
      (already lite; no need — just use the role)
A tier lists the providers it supports; if the role's provider isn't in the
tier, it SWITCHES (codex @ diff:10 -> Claude Fable; claude @ diff:2 -> Pi GLM).
When unsure, DO NOT GUESS a number — omit diff and trust the role.

HOW TO RUN (from the repo root)
  Sync (get the answer now):
    python .agents/dispatch.py ask \
      --role <role> [--diff N] [--account personal] \
      --cwd "<active workflow folder>" \
      --prompt "<task>"

  Async (queue, then collect later):
    TID=$(python .agents/dispatch.py handoff \
      --role <role> [--diff N] \
      --cwd "<active workflow folder>" --prompt "<task>")
    # a worker (local, or the VPS systemd timer) processes it
    python .agents/dispatch.py collect "$TID"

  (On the VPS, use `python3` instead of `python`.)

RULES
  - Set --cwd to the active workflow folder so the sub-agent reads the right
    directive and is bound by that folder's mcp-access.md. If no workflow folder
    applies, use the repo root.
  - Return the sub-agent's answer to the user (sync). For async, return the task
    id and say it will be processed by a worker; offer to collect when ready.
  - Mutating actions (publish/delete/deploy/email/billing/access changes) still
    require explicit confirmation - dispatch does not bypass that.
  - A sub-agent MAY dispatch again (depth limit 3) — e.g. a design agent handing
    the commit to `vcs`. Each hop is a COLD process with none of your context,
    so re-state everything it needs in the prompt.
  - If a provider CLI is missing, run: python .agents/dispatch.py doctor
